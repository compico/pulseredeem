# PulseRedeem — техническая памятка MVP

> Назначение документа: сохранить практические выводы первой реализации, чтобы перенести интеграцию Twitch → Яндекс Музыка в более крупный проект без повторения уже найденных проблем. Это описание текущего MVP и проверенных особенностей PulseSync, а не универсальная спецификация SDK.

## 1. Ограничения, проблемы и решения

### PulseSync SDK и очередь

| Проблема / ограничение | Причина | Решение / что учитывать при переносе |
|---|---|---|
| Команда добавления трека не подтверждает результат | `addTrackToQueueById()` — fire-and-forget: не возвращает Promise или статус вставки | Не считать вызов доказательством успешного добавления или начала воспроизведения. Отслеживать очередь через `getQueueSnapshot()` и `onQueueChange()`. |
| `position: 'last'` не подходит для заявок зрителей | В длинной очереди трек мог оказаться далеко за текущей последовательностью воспроизведения | Для заявки использовать `position: 'next'`, но не отправлять несколько таких команд подряд. |
| Повторные вставки в `next` могут менять порядок заявок | `injectNext` вставляет элемент после текущего индекса; следующая вставка попадает перед предыдущей | Реализована FIFO-диспетчеризация: одновременно вставляется только одна заявка. Следующая отправляется в PulseSync после того, как предыдущая стала текущим треком. |
| У SDK нет прямого подтверждения «трек начал играть» из команды вставки | Добавление в очередь и переход плеера к элементу — разные события | Запоминаются исходный `currentIndex` и ID ожидаемого трека. Через событие изменения очереди проверяется переход индекса и совпадение ID текущего элемента. Только после этого заявка снимается с головы локальной очереди. |
| Очередь плеера — не обычный массив «следующих треков» | Внутри player state есть `entityList`, индексы и порядок воспроизведения; shuffle может влиять на соответствие индекса элементу | В текущей реализации используется `snapshot.items[currentIndex]`. Это проверено на очереди с выключенным shuffle. При переносе обязательно проверить отображение индексов при shuffle/repeat и использовать фактический порядок воспроизведения, если SDK его предоставляет. |
| API может быть доступен до готовности плеера, но не всегда | Внутренний SDK helper `callWithPlayer` ставит вызов в pending, если player ещё не готов; если `window.pulsesyncApi` вообще отсутствует, вызов молча ничего не делает | Проверять наличие клиентских методов до использования. Не обращаться к внутреннему `window.__PULSESYNC__`: в исследованной версии публичный объект — `window.pulsesyncApi`. Предпочитать публичный SDK API, а не внутренние поля. |
| Локальная FIFO-очередь не переживает перезапуск | `trackRequests` и активная заявка хранятся в памяти runtime | Для MVP допустимо. В большом проекте сохранять ожидающие заявки в persistent storage/БД и восстанавливать их при старте; отдельно продумать сверку с уже вставленными треками, чтобы не создавать дубликаты. |

### Twitch и EventSub

| Проблема / ограничение | Причина | Решение / что учитывать при переносе |
|---|---|---|
| Для авторизации не нужен локальный callback-сервер | Используется OAuth Device Code Flow | Аддон показывает код и ссылку активации, затем опрашивает token endpoint. Twitch-приложение должно быть зарегистрировано как Public client. Redirect URL не участвует в этом потоке (в тестовой регистрации указывался localhost). |
| OAuth-токен нельзя просто обновлять «на месте» | Refresh token Device Flow ротируется и является одноразовым | Сразу сохранять одновременно новый access token и новый refresh token после каждого успешного refresh. Иначе следующее обновление может сломаться. |
| Успешный OAuth ещё не означает готовую интеграцию | Токен может иметь не те scopes или Client ID | После получения и при восстановлении сессии проверять токен через `/oauth2/validate`, Client ID и оба scope: `channel:read:redemptions`, `channel:manage:redemptions`. |
| Подписка EventSub требует ID текущей WebSocket-сессии | WebSocket сначала присылает `session_welcome`, в котором содержится session ID | Создавать EventSub subscription только после welcome. При `session_reconnect` подключаться к выданному `reconnect_url`, а не начинать обычную новую сессию. При разрыве соединения выполнять reconnect с задержкой. |
| WebSocket не является обычным HTTP-запросом SDK | В проекте EventSub подключается через WebSocket API среды выполнения; HTTP-запросы идут через `api.net.fetch` | В большом проекте явно проверить разрешения/политику окружения для WebSocket и домен EventSub. В конфигурации текущего аддона разрешён `wss://eventsub.wss.twitch.tv`. |
| Повторные уведомления могут прийти повторно | EventSub и reconnect не дают оснований считать доставку exactly-once | Дедуплицировать по redemption ID. В MVP ID хранятся в persistent storage (последние 2000) и дополнительно в Set текущего runtime. |
| Ошибочная ссылка не должна попадать в очередь | Пользовательский ввод зрителя — недоверенные данные | Валидировать URL до отправки в PulseSync. В MVP разрешены только HTTPS и домены Яндекс Музыки из allowlist; путь должен иметь вид `/album/{albumId}/track/{trackId}`. Не принимать произвольные URL и не пытаться извлекать ID из произвольного текста. |

### UI, сборка и установка

| Проблема / ограничение | Причина | Решение / что учитывать при переносе |
|---|---|---|
| Кнопка аддона должна появляться в предусмотренной точке интерфейса PulseSync | UI аддонов подключается через slots SDK, а не произвольным внедрением DOM | Зарегистрировать компонент в `defineAddon({ slots: { playerBarButton: ... } })`. Текущий UI — одна SDK-кнопка `IconButton` с иконкой gift и подписью «Подключить Twitch». Её обработчик обращается к runtime API. Не строить интеграцию на поиске DOM-элементов плеера. |
| Нельзя считать обычный React-компонент эквивалентом компонента SDK | Контракт UI определяется SDK и доступными slots/components | Использовать экспортируемые SDK-компоненты и поддерживаемые slots целевой версии PulseSync. При переносе проверить доступность нужного slot и компонентов именно в версии хоста, куда будет встроен проект. |
| В MVP UI не показывает полноценное состояние интеграции | Интерфейс намеренно ограничен одной кнопкой; статус и ошибки показываются уведомлениями/логами | Не предполагать наличие панели настроек, переключателя подключения, выбора награды или управления очередью. Если большой проект требует этого, спроектировать UI отдельно на официальных возможностях SDK. |
| SDK 0.18.0 в текущей конфигурации не создавал готовый `metadata.json` | Бандл собирался, но метаданные WebHost отсутствовали | Скрипт доставки генерирует manifest по официальной форме WebHost: `type: "web-addon"`, `script: "script.js"`, опционально `css`. Не использовать устаревшее поле `script` как тип аддона или legacy-формат манифеста. Валидировать manifest и существование файлов перед установкой. |
| Успешное копирование файлов не означает, что PulseSync загрузил аддон | Установка и перезагрузка хоста — разные операции | Скрипт после копирования вызывает dev endpoint `/dev/addons/reload?directory=...` с заголовком `X-PulseSync-Addon-Dev: 1`. Считать hot reload подтверждённым только при HTTP success и `payload.ok === true`; иначе сообщать, что нужен ручной перезапуск или endpoint не поддерживается. |
| Обновление не должно стирать пользовательские настройки аддона | Настройки лежат рядом с файлами аддона | При установке сохранять `pulsesync.settings.json`, использовать staging/backup и проверять путь назначения. Не перезаписывать store-managed addon без явного разрешения. |
| Dev-сборка и production-сборка — разные сценарии | Dev-скрипт следит за файлами и синхронизирует dist с каталогом аддонов | В проекте доступны `npm run dev`, `npm run build`, `npm run sync`, `npm run build:sync`; требуется Node.js 22.12+. На Windows стандартная папка — `%APPDATA%\\PulseSync\\addons\\pulseredeem`. |

## 2. Что необходимо от PulseSync для этой интеграции

### Минимальный контракт SDK

В текущем проекте зависимость зафиксирована на `@pulsesync/addon-sdk@0.18.0`. Аддон использует следующие публичные точки:

- `defineAddon(...)` — регистрация аддона, метаданных и UI slots.
- `start(api)` — точка запуска runtime; возвращаемая функция — cleanup при остановке/выгрузке.
- `api.client.addTrackToQueueById(trackId, options)` — отправка ID трека в очередь PulseSync. Для заявок используется `{ albumId, position: 'next' }`.
- `api.client.getQueueSnapshot()` — чтение текущего индекса и элементов очереди.
- `api.client.onQueueChange(callback)` — наблюдение за изменениями очереди; возвращает функцию отписки.
- `api.storage.get/set` — сохранение OAuth-токенов, ID награды и обработанных redemption ID.
- `api.net.fetch` — HTTP-запросы к Twitch из окружения аддона.
- `api.notifications.info/error` и `api.logger` — пользовательские уведомления и диагностика.
- `api.signal`, `api.setTimeout`, `api.setInterval` — отмена и таймеры, связанные с жизненным циклом аддона.
- `IconButton` и slot `playerBarButton` — отображение кнопки в панели плеера.

Для этой функциональности PulseSync не должен знать о Twitch, OAuth или формате пользовательской ссылки. Его роль — предоставить безопасный API аддона, persistent storage, UI slot и управление очередью.

### Поведение API очереди, важное для интеграции

Исследованная реализация SDK работает следующим образом:

1. `addTrackToQueueById` создаёт элемент очереди типа `unloaded` с ID, сформированным из track ID и, если передан, album ID.
2. Для `position: 'next'` SDK вызывает у player метод `injectNext`; для добавления в конец — `injectLast`.
3. Эти операции не возвращают подтверждение фактического воспроизведения.
4. Внутренний helper SDK вызывает callback сразу, если `playerInstance` уже доступен, или откладывает вызов до готовности player. Если глобальный API PulseSync отсутствует, helper просто возвращает управление.
5. `getQueueSnapshot()` предоставляет `currentIndex` и `items`; подписка `onQueueChange` позволяет отслеживать изменения. В текущем алгоритме этого достаточно при проверенном порядке элементов и выключенном shuffle.

**Практическое требование:** интеграция должна иметь собственный слой очереди заявок. Нельзя использовать повторные вызовы `position: 'next'` как FIFO-механизм и нельзя считать отправку команды подтверждением проигрывания.

## 3. Логика PulseRedeem и взаимодействие с PulseSync

### Старт и подключение

1. PulseSync загружает бандл и вызывает `start(api)`.
2. Аддон создаёт runtime: WebSocket, состояние остановки, наборы дедупликации, локальную очередь заявок и состояние активной заявки.
3. Аддон подписывается на `api.client.onQueueChange`; callback передаёт снимок очереди в FIFO-наблюдатель.
4. Из storage загружаются ранее обработанные redemption ID.
5. Если сохранён Twitch token существует, аддон валидирует его, при необходимости обновляет, проверяет scopes, находит/создаёт награду и подключается к EventSub.
6. Кнопка «Подключить Twitch» запускает Device Code Flow. Пользователь подтверждает код на Twitch; аддон сохраняет пару токенов, проверяет их и настраивает награду.

### Настройка Twitch

- Twitch Client ID встроен в аддон; Client Secret не используется.
- OAuth flow: Device Code → polling token endpoint → validate.
- Требуемые scopes: `channel:read:redemptions` и `channel:manage:redemptions`.
- Награда создаётся или переиспользуется по названию **«Заказать трек»**.
- Стоимость: **500 баллов**; обязательный ввод текста; prompt: «Вставь прямую ссылку на трек Яндекс Музыки».
- EventSub subscription: `channel.channel_points_custom_reward_redemption.add`, version `1`, transport WebSocket.
- При старте и переподключении используется сохранённая авторизация; refresh token сохраняется сразу после ротации.

### Обработка заявки зрителя

1. EventSub присылает redemption notification.
2. Аддон проверяет redemption ID: уже обработанные и уже обрабатываемые события игнорируются.
3. Событие фильтруется по ID выбранной награды — чужие награды не обрабатываются.
4. `user_input` проверяется парсером Яндекс Музыки. При неверной ссылке зритель получает уведомление, команда в PulseSync не отправляется.
5. Из ссылки извлекаются `trackId` и `albumId`.
6. Заявка добавляется в локальный FIFO-массив вместе с redemption ID и именем зрителя.
7. Если другая заявка не активна, первая отправляется в PulseSync через `addTrackToQueueById(trackId, { albumId, position: 'next' })`.
8. Redemption ID сохраняется в storage, чтобы повторная доставка EventSub не создала вторую заявку.
9. Пользователь получает уведомление, что заявка принята в очередь PulseRedeem. Это подтверждает приём заявки аддоном, но не является подтверждением начала воспроизведения.

### FIFO: подтверждение старта трека

- При вставке заявки аддон сохраняет текущий `currentIndex` как baseline и помечает заявку активной.
- При каждом `onQueueChange` сравнивает новый индекс с baseline и ID элемента по текущему индексу.
- Заявка считается начавшей воспроизводиться, только если индекс изменился и ID текущего элемента совпал с ожидаемым track ID.
- После этого активная заявка удаляется из головы локального массива, и следующая заявка отправляется как `next`.
- Если индекс не изменился или ID не совпал, заявка остаётся активной и следующая не вставляется.

Такой подход сериализует вставки и сохраняет порядок погашений. Это не полноценная гарантия доставки: API вставки не возвращает результат, локальная очередь volatile, а корректность сопоставления индекса с элементом должна быть повторно проверена для режима shuffle и целевой версии PulseSync.

### Остановка

При выгрузке аддон:
- помечает runtime остановленным;
- отписывается от `onQueueChange`;
- отменяет reconnect timer;
- закрывает Twitch WebSocket;
- очищает ссылку на активный runtime.

## 4. Что перенести в более крупный проект

Рекомендуется сохранить границы ответственности:

1. **Twitch adapter:** Device Code OAuth, refresh/validate, EventSub WebSocket, reconnect, подписка и нормализация redemption event.
2. **Input parser/validator:** строгая проверка URL Яндекс Музыки и извлечение идентификаторов.
3. **Request service:** дедупликация, persistent FIFO, статусы заявки и восстановление после перезапуска.
4. **PulseSync adapter:** тонкая обёртка над `addTrackToQueueById`, `getQueueSnapshot`, `onQueueChange`; здесь сосредоточить проверку версии SDK, shuffle и подтверждение фактического старта.
5. **UI:** подключение/отключение, статус Twitch, диагностика, настройки награды и отображение ожидающих заявок — через поддерживаемые UI slots/components PulseSync.
6. **Installer/build:** формирование WebHost metadata, проверка артефактов, безопасная установка без удаления пользовательских настроек и подтверждённая перезагрузка.

### Перед переносом обязательно проверить

- [ ] Версию PulseSync и совместимость SDK/host API.
- [ ] Наличие `playerBarButton` или подходящего slot в целевом UI.
- [ ] Доступность методов `addTrackToQueueById`, `getQueueSnapshot`, `onQueueChange`.
- [ ] Реальное поведение индексов при shuffle, repeat, удалении треков и ручном переключении.
- [ ] Сценарий, когда плеер не готов или отсутствует в момент вставки.
- [ ] Восстановление FIFO после перезапуска и защиту от повторной вставки.
- [ ] WebSocket permissions/allowed URLs для Twitch EventSub.
- [ ] Корректность OAuth refresh token rotation и хранения секретов.
- [ ] Формат WebHost metadata и путь установки в целевой версии PulseSync.
- [ ] Что уведомление «заявка принята» не выдаётся за подтверждение воспроизведения.
